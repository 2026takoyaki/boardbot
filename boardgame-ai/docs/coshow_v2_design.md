# CO-SHOW v2 설계 — 요트 턴 연출 · 늑대인간 개편 · IoT 조명

본 문서는 CO-SHOW 출품을 위한 v2 개발의 설계 기준을 정의한다.
세 갈래 작업(LLM/TTS 페르소나 · IoT 조명 · 늑대인간 개편)이 서로 의존하므로,
**착수 전에 인터페이스와 페이즈 계약을 먼저 고정**하는 것이 목적이다.

대상 독자: v2 개발에 참여하는 팀원 3인.

---

## 0. v2 목표와 방향 전환

| 항목 | v1 (캡스톤) | v2 (CO-SHOW) |
|---|---|---|
| 늑대인간 카드 인식 | 비전으로 역할·행동 인식 | **제거** — 인식 오류로 인한 수동 정정이 게임을 루즈하게 만듦 |
| 늑대인간 손 투표 | 지목 인식 시도 | **보류** — v2 범위 밖 |
| 분위기 연출 | 음성·화면만 | **IoT 조명 추가** — 물리 공간 연출로 몰입 강화 |
| TTS | 기계적인 톤 | 페르소나 부여로 자연스러움 개선 |
| 요트 | 기능 위주 | 턴 전환·득점 연출 추가 |

**핵심 전략:** "정확한 인식"에서 "확실한 몰입"으로 무게중심 이동.
인식 실패가 게임 흐름을 끊는 지점을 걷어내고, 대신 연출 밀도를 높인다.

### 부가 효과 — IoT 정체성 확보

v1에서 "센서가 카메라 하나뿐인데 IoT라 할 수 있나"라는 지적이 있었다.
조명이 들어오면 **센서(카메라) → 판정(FSM) → 액추에이터(조명)** 의 폐루프가 성립한다.
물리 세계를 읽기만 하던 시스템이 물리 세계에 개입하게 되므로, IoT 프레이밍이 실질적으로 강화된다.

## 1. 공통 설계 — Scene / Cue 2계층

### 1.1 왜 2계층인가

조명 연출에는 성격이 다른 두 종류가 있다.

| 계층 | 성격 | 수명 | 예시 |
|---|---|---|---|
| **Scene** | 페이즈가 유지되는 동안의 바탕 조명 | 페이즈와 동일 | 밤=어두운 남색, 낮=밝은 백색 |
| **Cue** | 순간적으로 터지고 Scene으로 복귀 | 0.5~3초 | 야찌 달성 번쩍, 턴 전환 스윕 |

**Cue의 계약: 반드시 Scene으로 복귀하며 끝난다.**
이 규칙이 있어야 조명이 이상한 상태로 멈춰 요트 주사위 인식을 망치는 사고를 구조적으로 막을 수 있다.

### 1.2 조명은 브로드캐스트 스트림의 구독자

조명 트리거를 TTS/SFX 호출 지점마다 심는 방식은 호출부가 흩어져 유지보수가 어렵다.
대신 **조명을 UI와 같은 계층으로 취급한다** — 프론트엔드가 `state_update`를 받아 다시 그리듯,
조명도 같은 메시지 스트림을 구독해 선언적으로 반응한다.

```
FSM ──WSMessage[]──▶ Session ──broadcast──┬──▶ Frontend (화면)
                                          └──▶ LightController (조명)
```

이 구조의 이점:

- FSM은 조명을 전혀 모른다 (`games/` 순수성 유지)
- 조명 트리거 누락이 원천적으로 발생하지 않음 (상태를 구독하므로)
- 하드웨어 없이 "어떤 Scene을 요청했는가"만 단언하면 테스트 가능
- 프론트 시각화 드라이버와 실제 전구가 자동으로 동기화됨

### 1.3 LightController 동작

```
on_message(msg):
    if msg.msg_type == STATE_UPDATE:
        phase = msg.payload["phase"]
        if phase != current_phase:
            apply_scene(SCENE_MAP[game][phase])
    elif msg.msg_type == CUE:
        play_cue(CUE_MAP[msg.payload["cue"]])   # 끝나면 현재 Scene 복귀
```

## 2. 요트다이스 수정안

### 2.1 현재 구조의 문제

`games/yacht/fsm.py` 의 `_handle_score_category()` 는 턴 전환을 이렇게 끝낸다.

```python
self.state.advance_player()
self.state.phase = YachtPhase.AWAITING_ROLL.value
self.state.last_message = f"{scorer_name}님 {score_label} {score}점입니다. ..."
return self._state_context_messages()
```

**턴이 넘어갔다는 명시적 이벤트가 없다.** `state_update` 안에서 `current_player`가 바뀔 뿐이다.
프론트엔드는 이를 diff로 추론하고 있다 (`YachtGame.jsx` 의 `turnPulseKey`, `recentScore`).

이 방식으로 모달을 띄우면 세 가지 문제가 생긴다.

1. **조명이 붙을 곳이 없다.** 조명은 백엔드에서 도는데, 프론트가 혼자 추론하면 백엔드는 그 순간을 모른다.
2. **데이터가 문자열에 갇혀 있다.** 연출에 필요한 `{누가, 어떤 족보, 몇 점, 특별한가}` 가 한국어 문장으로 뭉쳐 있다.
3. **재연결 시 오작동한다.** 상태 재동기화로 `current_player`가 다시 도착하면 턴이 안 바뀌었는데 모달이 뜬다.

### 2.2 해결 — CUE 메시지 추가

`MsgType` 에 `CUE = "cue"` 를 추가하고, 턴 전환 시 구조화된 payload를 함께 발행한다.

```python
# 턴 전환 시 state_update 와 함께 발행
WSMessage.make_cue(
    cue="yacht_turn_transition",
    payload={
        "scorer_id":    "p_2",
        "scorer_name":  "홍길동",
        "category":     "full_house",
        "category_label": "풀하우스",
        "score":        26,
        "is_highlight": False,        # 야찌·라지스트레이트 등 특별 족보
        "next_player":  "김철수",
        "duration_ms":  2200,         # 모달·조명 공통 타이밍 계약
    },
)
```

**이 메시지 하나가 모달 · 조명 Cue · TTS를 동시에 몬다.** 세 채널이 같은 `duration_ms`를 공유하므로 어긋나지 않는다.

### 2.3 모달 — 구현 결과

착수 전 초안은 늑대인간의 `PhaseTransition.jsx` 를 `components/common/` 으로
승격시켜 재사용하는 것이었다. **실제로는 별도 컴포넌트를 만들었다.**
`PhaseTransition` 은 내용 없이 화면만 덮는 전환 연출(눈 감기, 일출)인데, 요트는
누가·어떤 족보·몇 점·순위가 어떻게 바뀌었는지를 보여줘야 해서 성격이 다르다.

만들어진 것: `frontend/src/components/common/ScoreMoment.jsx`

| 시점 | 조건 | 길이 | 조명 |
|---|---|---|---|
| **주사위가 멈춘 순간** | 특별 조합 달성 | 1.2~2.8초 (조합별) | **관여 안 함** |
| 칸 확정 | 일반 득점 | 1.6초 | O |
| 칸 확정 | 특별 조합 | 1.8초 | O |
| 칸 확정 | 순위 상승 | 3.6초 | O |
| 칸 확정 | 0점 | 1.4초 | O |
| 상단 보너스 | 63점 돌파 | 2.6초 | 관여 안 함 |

**축하는 칸을 고른 뒤가 아니라 주사위가 멈춘 순간에 온다.** 짜릿한 건 눈이
맞아떨어진 순간이고 칸 선택은 그 뒤의 절차다. 굴림 구간은 조명이 관여하지 않으므로
(§2.4) 화면 연출을 가장 화려하게 가져갈 수 있고, 확정 쪽은 점수만 확인시켜준다.

조합별 강도는 희귀도에 비례한다 — 야찌 2.8초 · 라지스트레이트 2.4 · 포카드 1.8 ·
풀하우스 1.5 · 스몰스트레이트 1.2초.

> 페이싱 주의: v2의 취지가 "루즈함 제거"이므로 모달이 새로운 지루함이 되면 안 된다.
> 한 판이 36턴(12족보 × 3인)이라 몇백 ms가 그대로 늘어짐이 된다.
> 모달은 테두리·배경 없이 글자와 빛만 얹고, 탭 없이 자동으로 닫힌다.

### 2.4 요트 조명 제약 — 인식 보호가 최우선

주사위 인식은 YOLO 기반이라 **밝기뿐 아니라 색 분포 변화에도 취약**하다.
붉은 조명이 들어오면 학습 시점의 색분포와 어긋나 검출률이 떨어진다.

따라서 요트에는 강한 제약을 건다.

| 페이즈 | 조명 | 규칙 |
|---|---|---|
| `AWAITING_ROLL` | 중립 백색 (고정) | **어떤 Cue도 금지** — 굴림이 일어나는 구간 |
| `AWAITING_KEEP` | 중립 백색 | Cue 금지 |
| `AWAITING_SCORE` | 중립 백색 | Cue 허용 (굴림 종료 후) |
| 턴 전환 창 | Cue 재생 → 중립 복귀 | **모달 닫히기 전 복귀 완료 필수** |
| `GAME_END` | 축하 연출 | 자유 |

**불변식:** `모달 duration ≥ Cue 전체 길이(복귀 페이드 포함)`
모달이 닫히는 순간에는 이미 조명이 중립으로 돌아와 있어야 다음 굴림 인식이 안전하다.

### 2.5 측정 기회

조명 조건별 주사위 인식률(중립 / 컬러 / 저조도)을 벤치 하니스로 재면 표가 하나 나온다.
"연출과 인식 성능의 트레이드오프를 정량 측정했다"는 근거가 되므로,
v1에서 지적받은 Ablation 공백을 일부 메울 수 있다.

## 3. 늑대인간 개편안 (담당자 인계용)

### 3.1 제거 범위

카드 인식은 다음 파일에 결합되어 있다.

```
vision/detectors/card_detector.py     # YOLO 카드 감지
vision/tracking/card_tracker.py       # 카드 추적·역할 매핑
vision/werewolf/pipeline.py           # 파이프라인 조립
vision/fusion/werewolf_rules.py       # CARD_PEEK / CARD_SWAP 규칙
vision/fusion/engine.py               # 규칙 주입
games/werewolf/ontology.py            # 이벤트 타입 정의
games/werewolf/fsm.py                 # 이벤트 수신·페이즈 전이
backend/werewolf_session.py           # 세션 라우팅
backend/orchestrator.py               # 핸들러 등록
```

### 3.2 페이즈 전이 방식 변경

현재 밤 페이즈는 카드 이벤트가 전이를 몰고 있다.

| 역할 | 현재 | 변경 후 |
|---|---|---|
| 예언자 · 불면증환자 · 도플갱어 | `CARD_PEEK` 대기 | **타이머** |
| 도둑 · 말썽꾼 · 술꾼 | `CARD_SWAP` 대기 | **타이머** |
| 늑대인간 · 하수인 · 프리메이슨 | 이미 타이머 (`PASSIVE_PHASE_DURATION = 10s`) | 유지 |

**전이가 전부 타이머로 통일되면 페이즈 길이가 고정·예측 가능해진다.**
이는 조명 안무에 결정적이다 — 현재처럼 "카드가 언제 인식될지 모름" 상태에서는 연출 타이밍을 짤 수 없다.

역할별 소요 시간이 다르므로 페이즈별 타이머를 개별 지정한다 (초안).

| 페이즈 | 시간(초) | 근거 |
|---|---|---|
| `NIGHT_DOPPELGANGER` | 12 | 카드 확인 + 역할 이해 |
| `NIGHT_WEREWOLF` | 10 | 서로 확인만 |
| `NIGHT_MINION` | 10 | 확인만 |
| `NIGHT_MASON` | 10 | 확인만 |
| `NIGHT_SEER` | 15 | 선택 + 확인, 가장 김 |
| `NIGHT_ROBBER` | 12 | 교환 + 확인 |
| `NIGHT_TROUBLEMAKER` | 12 | 두 명 교환 |
| `NIGHT_DRUNK` | 10 | 교환만 (확인 불가) |
| `NIGHT_INSOMNIAC` | 8 | 자기 카드만 |

> 실제 값은 플레이테스트로 조정. 너무 짧으면 조급하고, 길면 루즈해진다.

### 3.3 ⚠️ 반드시 결정해야 할 것 — 최종 역할 판정

**카드 인식을 제거하면 시스템이 누가 무엇을 바꿨는지 모른다.**
도둑·말썽꾼·술꾼이 카드를 교환하면 최종 역할이 초기 역할과 달라지는데,
이를 추적할 수 없으면 `FINAL_ROLE_REVEAL` 에서 **승패 판정이 불가능하다.**

세 가지 선택지:

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A (권장)** | 결과 공개 시점에 각자 태블릿으로 최종 역할 1회 입력 | 행동마다 정정하는 것보다 훨씬 덜 루즈. 어차피 마지막에 공개하는 게임이라 자연스럽고, 그 순간을 연출로 승화 가능 | 입력 단계 1회 존재 |
| B | 밤 행동 자체를 태블릿으로 (도둑이 화면에서 대상 선택) | 인식 오류 0, 판정 완전 자동 | 물리 카드 경험이 깎임 |
| C | 판정 포기, 사회자 역할만 | 구현 최소 | 완성도 목표에 배치 |

**A안을 기본으로 설계한다.** 담당자가 카드 인식만 걷어내고 이 부분을 챙기지 않으면 게임이 끝나지 않으므로,
개편 작업의 필수 항목으로 포함한다.

> **[결정] IoT 조명은 이 결정을 기다리지 않는다.**
> 판정 방식은 늑대인간 담당자가 확정·구현하고, 조명은 **그 이후에 맞춰 추가**한다.
> 따라서 조명 모듈은 `RESULT` 페이즈에서 승리팀을 모르는 상태를 정상 경로로 취급해야 한다 (§5.1 참조).
> 판정이 확정되면 팀 색 분기만 매핑 테이블에 추가하면 되므로, 조명 작업이 블로킹되지 않는다.

### 3.4 페이즈 목록 동결

조명 매핑의 키가 페이즈 이름이므로 **이름은 계약이다.** v2에서도 기존 15개를 그대로 유지한다.

```
NIGHT_START · NIGHT_DOPPELGANGER · NIGHT_WEREWOLF · NIGHT_MINION · NIGHT_MASON
NIGHT_SEER · NIGHT_ROBBER · NIGHT_TROUBLEMAKER · NIGHT_DRUNK · NIGHT_INSOMNIAC
DAY_DISCUSSION · VOTE_COUNTDOWN · VOTE · FINAL_ROLE_REVEAL · RESULT
```

이름을 바꿔야 할 사정이 생기면 **조명 담당자와 먼저 합의**한다.

### 3.5 비전 유휴화

카드 인식 제거 + 손 투표 보류 → **밤 페이즈에 비전이 할 일이 없다.**
`FusionContext.expected_events` 가 비게 되므로 조명을 얼마든지 어둡게·화려하게 써도 잃을 것이 없다.

단, **좌석 등록은 게임 시작 전 lobby 파이프라인에서 수행**되므로 그 구간은 밝기를 유지해야 한다.

## 4. IoT 조명 모듈 설계

### 4.1 하드웨어

- Xiaomi Yeelight **컬러(RGB) 모델** — 빨강·초록 연출이 필요하므로 색온도만 되는 화이트 모델은 불가
- **수량: 1개** (확정)
- 제어 라이브러리: `python-yeelight`
- 연결: 로컬 LAN 직접 제어 (클라우드 경유 안 함)

#### 전구 1개라는 제약이 뜻하는 것

| 항목 | 함의 |
|---|---|
| 공간 연출 불가 | 좌석별 강조(지목 대상만 붉게) 같은 연출은 v2 범위 밖. 모든 효과는 **전역**이다 |
| 시간축 연출로 대체 | "스윕"은 공간 이동이 아니라 **색이 훅 들어왔다 빠지는 시간적 효과**로 구현한다 |
| 광량 한계 | 컬러 전구 1개는 대략 백열 60~75W 수준. 이것이 **유일한 광원**이므로 테이블에 가깝게 배치해야 한다 |
| 단일 장애점 | 전구가 죽으면 조명 연출뿐 아니라 **요트 주사위 인식까지 정지**한다 (§4.5, §4.7) |

**[결정] 배치: 오버헤드 카메라 바로 옆.** 테이블을 위에서 내리비추는 형태.

카메라와 광원이 거의 같은 축에 놓이는 배치라 다음 트레이드오프가 있다.

| | 영향 |
|---|---|
| ✅ 그림자 최소 | 광원과 시점이 같은 방향이라 물체 그림자가 물체 뒤에 숨는다. 손이 들어와도 주사위에 드리우는 그림자가 카메라에 덜 보인다 |
| ⚠️ 정반사 위험 | 광택 있는 주사위·트레이 표면에서 **하이라이트가 카메라로 직접 되튄다.** pip 인식(HoughCircles)이 반사점을 pip으로 오검출하거나, 반사가 pip을 덮을 수 있다 |

정반사가 실제로 문제가 되면 디퓨저를 씌우거나 각도를 살짝 틀어 대응한다.
**실물 확인이 필요한 항목이다** (§9 점검).

### 4.2 패키지 구조

```
bulb/
  __init__.py         # build_controller() 팩토리 + 드라이버 폴백
  controller.py       # LightController — 메시지 구독, Scene/Cue 상태 관리
  scenes.py           # Scene·Cue 정의 + 게임별 매핑 테이블
  config.py           # 전구 IP, 활성화 플래그, 게임별 밝기 하한
  driver/
    base.py           # LightDriver ABC
    yeelight.py       # 실제 전구 제어
    mock.py           # 로그만 출력 (기본값)
    frontend.py       # WS로 프론트에 색 전달 (개발 시각화 + 폴백)
tools/
  light_check.py      # 30초 현장 점검 스크립트
```

> 패키지 이름을 `iot`가 아니라 `bulb`로 둔다. 이 모듈이 다루는 것은 전구
> 하나이고, 나중에 다른 장치가 붙으면 형제 모듈로 추가하면 된다.
> `iot`라는 이름은 장치 하나짜리 모듈이 IoT 전체를 대표하게 만든다.

### 4.3 드라이버 인터페이스

```python
class LightDriver(ABC):
    async def apply(self, color: RGB, brightness: int, duration_ms: int) -> None: ...
    async def close(self) -> None: ...
```

구현 3종:

| 드라이버 | 용도 | 기본값 |
|---|---|---|
| `MockDriver` | 로그만 출력 | ✅ 개발 기본 |
| `FrontendDriver` | 화면에 색 띠 표시 | 개발 시각화 + **전구 실패 시 폴백** |
| `YeelightDriver` | 실제 전구 | 환경변수로 opt-in |

**하드웨어 없이 연출 전체를 완성하고 검증할 수 있어야 한다.**
`FrontendDriver`는 테스트 당일 전구가 안 붙어도 화면으로 분위기를 대체하는 안전망 역할을 겸한다.

### 4.4 Orchestrator 연결

`backend/orchestrator.py` 는 이미 세터 주입 패턴을 쓴다
(`set_audio_manager`, `set_pipeline_switcher`, `set_broadcast`).
조명도 동일하게 붙인다.

```python
orchestrator.set_light_controller(light_controller)
```

기존 관례를 따르므로 구조적 이물감이 없다.

### 4.5 안전 정책 (필수)

| 항목 | 정책 | 이유 |
|---|---|---|
| **비동기 · fire-and-forget** | 조명 명령은 FSM/오디오 스레드를 절대 블로킹하지 않음 | 소켓 지연이 게임 진행을 멈추면 안 됨 |
| **타임아웃** | 명령당 짧은 타임아웃 후 포기 | 전구 응답 없음이 게임을 끌면 안 됨 |
| **실패 무시** | 조명 예외는 로깅만, 게임 로직은 계속 | **조명 코드가 게임을 깨뜨릴 권한은 없다** |
| **물리적 실패는 별개** | 전구 자체가 죽으면 소프트웨어로 복구 불가 → 운영 폴백(천장등 수동 점등) | 단일 광원이라 요트 인식이 물리적으로 정지한다 (§4.7) |
| **명령 병합** | 직전과 동일한 (색, 밝기)는 재전송하지 않음. **단 실패한 명령은 캐시하지 않는다** | Yeelight 분당 명령 수 제한 회피. 실패를 캐시하면 뒤이은 중립 복귀가 중복 제거로 삼켜져 인식이 깨진다 |
| **밝기 하한** | **게임별로 다르다** (아래 참조) | 요트는 인식, 늑대인간은 연출이 우선 |
| **종료 시 복원** | 게임 종료·프로세스 종료·세션 끊김 시 중립 조명 복귀 | 다음 세션 오염 방지 + Cue 도중 끊김 복구 |
| **부팅 시 점등** | 서버 기동 직후 중립 적용 (`controller.start()`) | 로비는 세션을 거치지 않고 브로드캐스트해서 조명 스트림에 잡히지 않는다. **좌석 등록 구간의 밝기는 이 기본값이 유일한 보장이다** (§3.5) |

#### 밝기 하한은 게임별 정책이다

초기 안은 "밤에도 최소 밝기 유지"였으나 이는 늑대인간 연출과 충돌한다.
"밤이 되었습니다"는 **완전한 암전**에서 시작해야 하고, 거기서 "늑대인간은
일어나세요"에 맞춰 붉은 빛이 스며들어야 장면이 산다. 하한을 드라이버에
박아두면 이 연출이 불가능하다.

따라서 **소등은 드라이버가 허용하고**(`brightness=0`은 최저 밝기가 아니라
소등이다), **하한은 게임별 정책으로** 컨트롤러가 강제한다.

| 컨텍스트 | 하한 | 근거 |
|---|---|---|
| `yacht` | 높음 (초기값 60) | 이 전구가 곧 주사위 인식 조명이다. §7.2-7에서 실물로 확정 |
| `werewolf` | **0 (완전 소등 허용)** | 밤에는 비전이 할 일이 없다 (§3.5) |
| `lobby` | 높음 (초기값 60) | 좌석 등록이 비전으로 돌아간다 (§3.5) |
| 미지정 | 높음 | 비전이 돌고 있을지 모르는데 어둡게 하느니 연출을 포기한다 |

매핑 테이블이 실수로 어두운 값을 넣어도 컨트롤러가 걷어올리므로,
요트에서 인식이 죽는 사고가 구조적으로 막힌다.

### 4.6 Yeelight 실전 함정 (테스트 당일 대비)

| 함정 | 내용 | 대비 |
|---|---|---|
| **LAN 제어 미활성** | Mi Home 앱에서 "LAN 제어"를 켜야만 제어 가능. **기본 꺼져 있음** | 전구 수령 즉시 활성화 |
| **2.4GHz 전용** | 5GHz WiFi에 붙지 않음 | 폰 핫스팟(2.4GHz) 백업 준비 |
| **SSDP 멀티캐스트 차단** | `discover_bulbs()` 는 멀티캐스트를 쓰는데 폰 핫스팟에서 동작할지 **장담할 수 없다** | **IP 직접 지정을 기본 경로로**, 탐색은 편의 기능. 핫스팟은 주소 대역이 좁아 포트 스캔이 더 빠르다 (§4.8) |
| **명령 rate limit** | 분당 약 60회 초과 시 무시·연결 끊김 | 명령 병합, 필요 시 music mode |
| **전환 품질** | 급격한 전환은 싸구려 느낌 | `effect="smooth"`, `duration` 800~1500ms |

### 4.7 단일 광원 전제 — 설계의 근간

**[결정] 우리 전구 1개가 유일한 광원이다.** 천장등이 없는 상태를 기본 전제로 설계·개발·시연한다.

- 시연 영상 촬영: 통제된 장소를 확보해 완전 소등 상태에서 촬영
- 현장 시연: 소등 또는 암막 커튼으로 공간을 만들어 대응
- **천장등은 폴백**: 요트 주사위 인식이 정 안 될 경우에만 켜서 유연 대응

이 전제가 갖는 함의는 크다.

#### ① 조명이 곧 인식 인프라다

요트 주사위 인식이 **전적으로 이 전구에 의존**한다. 따라서:

- `AWAITING_ROLL` 구간의 **중립 백색 최대 밝기는 연출이 아니라 인식 요구사항**이다
- **Cue 복귀 실패 = 인식 실패**로 직결된다. §2.4의 복귀 보장 불변식이 단순한 안전장치가 아니라 필수 요건이 된다
- 전구 고장·연결 끊김은 소프트웨어로 복구할 수 없다 → **운영 폴백(천장등 수동 점등)이 유일한 대응**

#### ② 반대로, 요트에서도 조명 연출이 확실히 보인다

주변광이 없으므로 색을 바꾸면 **장면 전체가 그 색으로 물든다.**
"전구 1개 색 변화는 천장등에 묻힌다"는 우려는 이 전제에서 사라진다.

따라서 두 게임의 관계는 다음과 같이 정리된다.

| | 요트다이스 | 늑대인간 |
|---|---|---|
| 조명 효과 가시성 | **높음** (단일 광원) | 높음 |
| 비전 의존 | 있음 (주사위) | 없음 |
| 조명 자유도 | **허용된 창에서만** — 턴 전환·게임 종료 | **상시 자유** |
| 위험 | 색 변경이 인식을 직접 망침 | 없음 |

> **결론: 두 게임 모두 조명이 주요 연출 채널이다.**
> 다만 요트는 "쓸 수 있는 시점"이 엄격히 제한되고, 늑대인간은 제약이 없다.
> 위험도가 낮고 자유도가 높은 **늑대인간부터 구현**하고, 요트는 복귀 보장을 확실히 한 뒤 붙인다.

#### ③ 밤 최저 밝기가 실질적인 유일 변수다

천장등이 없으므로 늑대인간 밤의 어둠은 **전구 밝기만으로 결정된다.**
"어둡되 최소한 보이긴 해야 한다"는 요구를 만족하는 값을 실물로 찾아야 한다 (§7.2).

### 4.8 네트워크 구성 — 폰 핫스팟 전제

**[결정] 폰 핫스팟을 네트워크로 사용한다.**
학교 유선망을 공유기에 연결하는 방식은 망 정책상 차단 우려가 있어 채택하지 않는다.

```
        [폰 A] ── 핫스팟 (2.4GHz)
           │
     ┌─────┼─────┐
     │     │     │
  노트북  패드   전구
 (서버·비전) (UI)  (조명)
```

#### 이미 검증된 것

노트북과 패드가 이 핫스팟에서 통신하고 있다.
이는 **핫스팟이 클라이언트 간 통신을 차단하지 않는다(AP isolation 없음)**는 증거다.
전구도 같은 서브넷의 클라이언트가 되므로 노트북에서 접근 가능하다.

#### 필수 조건

| 조건 | 내용 |
|---|---|
| **2.4GHz** | Yeelight는 5GHz에 연결되지 않는다. 아이폰은 **"호환성 최대화(Maximize Compatibility)"** 를 켜야 2.4GHz로 내려온다. 안 켜면 전구가 네트워크에 진입조차 못 한다 |
| **셋업 시 인터넷** | Mi Home 최초 등록에는 클라우드 통신이 필요하므로 핫스팟에 셀룰러 데이터가 살아 있어야 한다. **LAN 제어를 켠 뒤에는 인터넷 없이 로컬 제어만으로 동작**한다 |
| **폰 2대** | 핫스팟을 제공하는 폰으로는 등록이 어렵다 (아래 참조) |

#### 아이폰 핫스팟 주소 대역

`172.20.10.x` 대역이 정상이다. 다만 **/28 서브넷이라 최대 14대**만 수용한다
(노트북 + 패드 + 전구 = 3대이므로 문제 없음).

주소가 좁다는 점은 오히려 장점이다 — **전구 IP를 전수 스캔으로 1초 만에 찾을 수 있다.**

```bash
# Yeelight 제어 포트(55443)가 열린 호스트만 찾는다
nmap -p 55443 --open 172.20.10.0/28
```

#### 2.4GHz 전환의 부작용

노트북·패드도 2.4GHz로 붙게 되어 대역폭이 줄어든다.
WebSocket 메시지와 TTS 오디오에는 충분하지만,
**프론트엔드를 Vite 개발 서버로 서빙하면 초기 로딩이 체감될 수 있다.**
시연에서는 빌드된 정적 파일을 서빙하는 편이 안전하다.

#### ⚠️ 핫스팟 고유의 위험

| 위험 | 영향 | 대응 |
|---|---|---|
| 전화 수신·화면 잠금 | 핫스팟 중단 → **노트북·패드·전구 동시 단절** | 시연 중 해당 폰 방해금지 + 화면 켜둠 |
| 연결 기기 없을 때 자동 종료 | 세션 시작 전 꺼져 있음 | 시연 직전 재확인 |
| 폰 소유자 부재 | 전체 시스템 정지 | 소유자 동석 필수 |
| DHCP 주소 변동 | 전구·노트북 IP가 매번 달라질 수 있음 | 매 세션 `light_check` 로 IP 재확인 |

핫스팟이 **단일 장애점**이라는 점을 인지하고 운영한다.
조명뿐 아니라 패드 UI까지 함께 끊기므로, 시연 중 이 폰의 상태 관리가 중요하다.

### 4.9 전구 최초 셋업 절차

전구를 처음 받았을 때 한 번 수행한다.
**전구는 등록한 네트워크 하나만 기억하므로, 실제 시연에 쓸 핫스팟으로 등록해야 한다.**
(집 WiFi로 등록해두면 현장에서 연결되지 않는다.)

#### 준비

- **폰 A**: 핫스팟 제공 (시연에 쓸 그 폰)
- **폰 B**: Mi Home 실행용 (본인 폰 권장 — 계정이 본인 것으로 잡힌다)

> **왜 폰 2대인가:** 등록 과정에서 폰이 전구의 임시 AP에 접속했다 돌아와야 하는데,
> 폰이 WiFi 클라이언트가 되는 순간 자기 핫스팟이 꺼진다 (같은 무선 칩을 사용).
> 핫스팟 제공 폰으로는 이 과정을 완주할 수 없다.

#### 절차

1. **폰 A** 핫스팟 켜기 — 설정에서 **"호환성 최대화" ON** (2.4GHz 강제), 셀룰러 데이터 ON
2. **폰 B** 를 폰 A 핫스팟에 연결
3. **폰 B** 에 **Mi Home** 설치 후 Xiaomi 계정 로그인
   - ⚠️ **지역 설정**을 싱가포르 또는 한국으로. 지역에 따라 Yeelight 기기가 목록에 안 뜨는 경우가 있다
4. 전구를 소켓에 꽂고 전원 ON — 페어링 대기 상태로 켜진다
   - 반응이 없으면 **전원을 5회 껐다 켜기** (약 2초 간격) → 색이 순환하며 깜빡이면 초기화 완료
5. Mi Home → **기기 추가(+)** → 자동 검색되거나, 수동으로 조명 카테고리에서 Yeelight 선택
6. WiFi 선택 화면에서 **폰 A 핫스팟 SSID + 비밀번호** 입력
7. 등록 완료까지 대기
8. **🔑 LAN 제어 켜기 (가장 중요)**
   - Mi Home → 해당 전구 → 우측 상단 **⋯(더보기)** → 설정 → **"LAN 제어" / "LAN Control"** → **ON**
   - 이 항목이 안 보이면 **Yeelight 앱**을 따로 설치해 같은 계정으로 로그인 → 기기 설정에서 LAN 제어 활성화
   - 앱 버전·펌웨어에 따라 위치가 다르므로 두 경로를 모두 확인한다
9. 노트북에서 연결 확인

```bash
python -m tools.light_check          # discovery 시도 → 실패 시 수동 IP 안내
nmap -p 55443 --open 172.20.10.0/28  # discovery 실패 시 IP 직접 탐색
```

#### 셋업 후 기억할 것

- **LAN 제어는 기본이 꺼져 있다.** 이걸 안 켜면 `python-yeelight` 가 아무리 해도 접속하지 못한다
- **네트워크를 바꾸면 4~8단계를 다시 해야 한다** — 핫스팟 SSID·비밀번호가 바뀌면 재등록
- 제어 포트는 **55443** (고정)
- 등록이 끝나면 인터넷 없이도 제어된다 — 시연장에서 데이터가 끊겨도 조명은 동작

## 5. 조명 매핑 테이블

### 5.1 늑대인간

색은 역할마다 다르게 하기보다 **의미 단위로 묶는다.** 10색을 다 쓰면 산만하고 촌스럽다.

| 페이즈 | 색 계열 | 밝기 | 전환 | 의도 |
|---|---|---|---|---|
| `NIGHT_START` | **완전 소등** | 0 | 2000ms 서서히 | "밤이 되었습니다" — 암전에서 시작한다 |
| `NIGHT_DOPPELGANGER` | 보라 | 낮음 | 1200ms | 특수 |
| `NIGHT_WEREWOLF` | 적색 | 낮음 | 1200ms | 악역. 암전에서 붉은 빛이 스며든다 |
| `NIGHT_MINION` | 적색(약) | 낮음 | 1200ms | 악역 |
| `NIGHT_MASON` | 초록 | 낮음 | 1200ms | 마을 |
| `NIGHT_SEER` | 청/인디고 | 낮음 | 1200ms | 정보 |
| `NIGHT_INSOMNIAC` | 청/인디고 | 낮음 | 1200ms | 정보 |
| `NIGHT_ROBBER` | 앰버 | 낮음 | 1200ms | 교란 |
| `NIGHT_TROUBLEMAKER` | 앰버 | 낮음 | 1200ms | 교란 |
| `NIGHT_DRUNK` | 앰버 | 낮음 | 1200ms | 교란 |
| `DAY_DISCUSSION` | 따뜻한 백색 | **높음** | **2500ms 일출** | ★ 감정의 정점 |
| `VOTE_COUNTDOWN` | 적색 기운 | 중간 | 서서히 조임 | 긴장 고조 |
| `VOTE` | 적색 | 중간 | 1000ms | 결단 |
| `FINAL_ROLE_REVEAL` | 중립 백색 | 높음 | 800ms | 명확히 보여야 함 |
| `RESULT` (1차) | 중립 축하 | 높음 | 1500ms | **팀 무관** — 판정 확정 전 기본 동작 |
| `RESULT` (2차) | 승리팀 색 | 높음 | 1500ms | 늑대=적 / 마을=청록. 판정 구현 후 추가 |

> `RESULT` 는 승리팀을 모르는 상태를 **정상 경로**로 취급한다 (§3.3 결정).
> 판정 방식이 확정되기 전까지는 팀 무관 축하 연출로 동작하고,
> 늑대인간 담당자가 판정을 구현한 뒤 팀 색 분기를 매핑에 추가한다.
> 조명 모듈은 승리팀 정보가 없어도 예외 없이 동작해야 한다.

**밤→낮 전환(`dawn`)에 가장 공을 들인다.** 어둠에서 따뜻한 빛이 2.5초에 걸쳐 차오르며
TTS가 얹히는 구간이 이 게임의 감정적 클라이막스다.
프론트엔드 `PhaseTransition.jsx` 의 `dawn` 타입(duration 2500, midAt 300)과 타이밍을 맞춘다.

**정보 누출 우려 없음:** "늑대인간은 깨어나세요"라고 TTS가 이미 공개적으로 알리므로,
색이 추가로 흘리는 정보가 없다. (심사 질의 대비 근거)

### 5.2 요트다이스

Scene은 예외 없이 중립이다.

| 페이즈 | 색 | 밝기 |
|---|---|---|
| `AWAITING_ROLL` / `AWAITING_KEEP` / `AWAITING_SCORE` / `GAME_END` | **중립 백색 고정** | 100 |

Cue는 **WS 메시지의 `cue` 키**로 조회한다. 아래 첫 열이 실제 키이고, 둘째 열은
`bulb/scenes.py` 안에서 붙인 패턴 이름이다 — 코드를 찾을 때는 첫 열로 검색한다.

| 메시지 키 (`payload.cue`) | 패턴 이름 | 색 | 밝기 | 복귀까지 / 예산 |
|---|---|---|---|---|
| `yacht_turn_transition` | `turn_sweep` | `(255,226,178)` | 100 | 1400ms / 1600ms |
| `yacht_turn_transition_highlight` | `score_burst` | `(255,214,140)` | 100 | 1550ms / 1800ms |
| `yacht_turn_transition_lead_change` | `upset_flash` | `(196,226,255)` | 100 | 2350ms / 3600ms |
| `yacht_turn_transition_zero` | `deflate` | `(214,224,238)` | 100 | 1250ms / 1400ms |
| `yacht_game_finish` | `game_finish` | `(255,200,90)` | 100 | 3800ms / 4000ms |

`_highlight` / `_lead_change` / `_zero` 는 FSM이 payload에 실어 보내는 `variant`로
갈린다. 매핑에 변형이 없으면 기본 키로 떨어지므로 새 variant가 생겨도 깨지지 않는다.

> **`yacht_hand_achieved`(굴림 축하)는 이 표에 없다.** 매핑에 이름이 없으면 조명이
> 무시하는데, 그게 의도다 — 굴림 구간은 주사위 인식이 걸린 곳이라 조명이 흔들려선
> 안 된다. 그 순간의 연출은 화면이 전담한다.

#### 요트 연출은 색을 갈아엎지 않고 톤만 얹는다

늑대인간 팔레트를 그대로 가져오면 안 된다. 요트는 이 전구가 곧 주사위 인식
조명이라 **원색이 들어오면 YOLO가 학습 시점과 다른 색분포를 본다.**

따라서 요트 Cue는 두 가지를 지킨다.

| 규칙 | 값 |
|---|---|
| **밝기 불변** | 세 Cue 모두 100 고정. 광량이 흔들리면 그대로 인식 위험 |
| **저채도 유지** | 플레이 중 Cue는 가장 어두운 채널이 130 이상 — 원색이 아니라 백색 틴트 |

단일 광원이라 이 정도 색온도 변화로도 방 전체가 물들어 충분히 보인다.
**연출의 세기는 조명이 아니라 화면 모달이 감당한다.**

예외는 `game_finish` 하나다. 게임이 끝나면 더 굴릴 주사위가 없으므로
인식 제약에서 자유롭고, 여기서만 원색을 쓴다.

#### `GAME_END` Scene도 중립이다

축하는 **Cue가 터뜨리고 곧바로 기본색으로 돌아온다.** Scene 자체를 금색으로
두면 두 가지 문제가 생긴다.

1. 축하가 끝나지 않고 그 색에 머무른다 — 다음 세션까지 오염된다
2. Cue와 색이 같아 **중복 제거에 걸려 연출이 통째로 사라진다**
   (실제로 이 상태였고, 전구에 나가는 명령이 Scene 하나뿐이었다)

> **좌석 색을 쓰지 않기로 했다.** 초안은 "해당 플레이어 좌석 색이 들어왔다
> 빠짐"이었으나, 프론트 좌석 색은 oklch 파스텔(C≈0.12)이라 전구 하나로
> 재현하면 10색이 전부 "살짝 물든 흰색"으로 뭉갠다. 누구 차례인지는 화면과
> TTS가 이미 말하므로, 조명은 **"턴이 넘어갔다"만 분명히** 전한다.

**페이즈 값 규약이 게임마다 다르다.** 요트는 대문자(`AWAITING_ROLL`),
늑대인간은 소문자(`night_start`)다. 매핑 키를 손으로 적으면 오타가 조용히
중립 폴백으로 흡수돼 눈치채기 어려우므로, **테이블 키는 enum에서 가져온다.**

요트는 **Scene이 항상 중립**이고 Cue만 일시적으로 벗어나는 구조다.

> **단일 광원이라 색 변화가 확실히 보인다**(§4.7). 요트에서도 조명은 충분히 강력한 연출 채널이다.
> 다만 같은 이유로 **위험도 크다** — 이 전구가 곧 인식 조명이므로,
> Cue가 중립으로 복귀하지 못하면 다음 굴림 인식이 바로 망가진다.
> `AWAITING_ROLL` 중립 고정과 복귀 보장은 연출 규칙이 아니라 **인식 요구사항**으로 다룬다.

## 7. 결정 사항 및 잔여 과제

### 7.1 확정된 결정

| # | 항목 | 결정 | 영향 |
|---|---|---|---|
| 1 | 최종 역할 판정 방식 | **IoT 조명은 대기하지 않음.** 늑대인간 담당자가 확정·구현한 뒤 조명을 맞춰 추가 | `RESULT` 는 팀 무관 축하가 기본 동작 (§5.1) |
| 2 | 전구 개수 | **1개** | 공간 연출 불가, 전역 효과만. 시간축 연출로 대체 (§4.1) |
| 3 | 주변광 | **우리 전구가 유일한 광원.** 천장등 없는 상태가 기본 전제 | 설계 전반의 근간 (§4.7) |
| 4 | 전구 배치 | **오버헤드 카메라 바로 옆** | 그림자 최소화 ↔ 정반사 위험 트레이드오프 (§4.1) |
| 5 | 천장등 사용 | **폴백 전용** — 요트 인식이 정 안 될 때만 | 유연 대응 여지 확보 |
| 6 | 네트워크 | **폰 핫스팟** (2.4GHz 강제). 학교 유선망+공유기는 망 정책상 배제 | 노트북·패드·전구가 한 서브넷. 핫스팟이 단일 장애점 (§4.8) |

이 결정들에서 파생된 핵심 방침:

> **두 게임 모두 조명이 주요 연출 채널이다.**
> 요트는 쓸 수 있는 시점이 엄격히 제한되고(턴 전환·종료), 늑대인간은 제약이 없다.
> **늑대인간부터 구현**하고, 요트는 Cue 복귀 보장을 확실히 한 뒤 붙인다.
>
> 단일 광원이므로 **조명 = 인식 인프라**다. 전구 실패는 요트 인식 정지로 직결되며,
> 소프트웨어가 아니라 운영(천장등 수동 점등)으로만 복구된다.

### 7.2 잔여 과제 (플레이테스트로 수렴)

| # | 항목 | 초안 | 확정 방법 |
|---|---|---|---|
| 7 | **요트 인식 가능 최저 광량** | 미정 | 전구 1개로 주사위 인식이 되는지. 안 되면 천장등 폴백 발동 |
| 8 | **밤 최저 밝기** | 15 (`LIGHT_NIGHT_BRIGHTNESS`) | 단일 광원이라 이 값이 밤의 어둠을 전적으로 결정. "어둡되 보이긴 해야" 하는 지점을 실물로 탐색. 환경변수 하나로 모든 밤 페이즈가 함께 움직인다 |
| 9 | 정반사 대응 필요 여부 | 미정 | 카메라 옆 배치에서 pip 오검출이 생기는지 확인 후 디퓨저·각도 조정 |
| 10 | 핫스팟에서 SSDP 동작 여부 | 미정 | 되면 discovery, 안 되면 포트 스캔으로 IP 확보 |
| 11 | 밤 페이즈 타이머 값 | §3.2 (8~15초) | 실제 플레이로 조정 |
| 12 | 요트 모달 지속시간 | 2.2초 | 페이싱 감각 문제 |

7·8·9·10번은 **전구 입수 즉시 확인해야 할 항목**이다. 특히 7번이 부정적이면 요트 운영 방식이 바뀐다.

## 9. 테스트 당일 점검 순서

0. **핫스팟 준비** — 폰 A 핫스팟 ON, **"호환성 최대화" 켜져 있는지 확인**(2.4GHz), 방해금지·화면 켜둠
1. `tools/light_check.py` 실행 — 전구 연결·색 변경 확인 (30초)
   - 실패 시 `nmap -p 55443 --open 172.20.10.0/28` 로 IP 재확보
2. 천장등 소등 (기본 전제) — 스위치 또는 암막 커튼
3. 전구를 카메라 옆에 고정, 테이블 조사 범위 확인
4. **소등 상태에서 전구 1개만으로 요트 주사위 인식이 되는지** ★ 가장 중요
   - 실패 시 → 천장등 폴백 발동, 요트 조명 연출은 축소
